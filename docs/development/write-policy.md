# Offline guarded-write policy

Production writes are **unavailable**. No verified device policy, YAML opt-in, packet encoder or scheduler bridge is shipped. The root never constructs this module or enables TX. Catalog research does not authorize an equipment action. Positive tests use a synthetic policy and do not establish a verified family or actual write success.

The pure C++ Guard is future infrastructure with an immutable copied policy and no UART/scheduler access. It cannot be copied or moved because outstanding tickets and rate history must not be duplicated. Admission requires explicit opt_in, verified_family, unicast device address, controller address, a bounded per-device code allowlist, finite physical min/max/step, valid typed conversion and an exactly representable raw scalar. The re-decoded wire value is checked again against physical min/max and step, and must match the requested value within eight double-precision epsilons relative to magnitude. Raw/integer step checks use the same roundoff scale. Physical min/max are never expanded by tolerance; a boundary that cannot satisfy these checks is rejected. Descriptor raw ranges, allowed values and sentinels also apply. There are at most 8 rules, no automatic retries and one outstanding intent. An external mutation of the original policy cannot enable an existing Guard.

Admission rate is measured from preparation and then actual successful TX completion, with a minimum 1000 ms interval. Preparation is bounded 100–5000 ms, readback 100–60000 ms, and rate 1000–60000 ms. Public code cannot toggle an instance back on. A preparation deadline with unknown transmission outcome or a failed send creates a sticky fault requiring reconstruction; a readback timeout retires the intent without retry and retains rate history. All entry points enforce deadlines, including late event/readback arrival and uint32 clock rollover. Only the matching outstanding ticket can begin the actual-TX readback timer.

Readback accepts only Notification/Response from the exact target to the configured local controller, matching code and exact raw value after typed validation. ACKs never complete an intent. Readback before actual TX is ignored; unrelated source/destination/code, invalid values, stale tickets and overdue packets cannot match. OBSERVED_MATCH means the requested state was observed, not proof that this integration caused it. Broadcast-directed observations do not satisfy this conservative offline policy. The module creates only a typed scalar ticket, never a bus frame.

The verified_family flag is a trusted policy author's prerequisite assertion, not a cryptographic proof or a substitute for capture review. A future active bridge must supply capture-backed immutable model/code/range policies, one Guard per device, actual scheduler completion/cancellation events, fresh observation timing, restart/fault handling, bus serialization and explicit authorization for physical testing. It must not turn user-entered evidence into approval. No such bridge or approved family exists here.

Tests cover opt-in/family/device/code gates, finite ranges/steps and signed wire representation, serialization/rate limits, actual completion, strict readback/ACK behavior, preparation/readback deadlines, stale tickets, send faults, copy prevention and rollover. This satisfies software policy testing only. Hardware write safety, controller ownership, real timing and equipment readback remain BLOCKED/NOT TESTED until identified hardware evidence and authorized pilot work exist.
